# B4：从 9X 配置表快照提取结构化 JSON

本步只验证一份 9X 分组配置表；未解析其他车型，也未规范化或入库。

| 子步骤 | 实现 |
| --- | --- |
| B4.1 | 选取 B2 的 9X 配置快照。表头由 `.version-item` 和 `.model-item` 构成；分组的 `flex` 数字对应列数。 |
| B4.2 | 逐个读取 `.parameterList-item`，按位置关联版本列和单元格，保留层级、描述和原文。 |
| B4.3 | 从 `sup` 读取脚注编号，从 `.config-tips` 读取对应说明；记录来源 URL、采集时间、批次及两个输入文件的路径和哈希。 |
| B4.4 | 使用合成 HTML 样本做离线测试，并抽查真实 9X 表格。 |

列、行和单元格的列号均从 1 开始，按 DOM 顺序排列。两个同名 Ultra 版分别保留在第 2 列（六座）和第 5 列（五座）。行名不含脚注上标，`raw` 保留由 HTML 提取的文字，`footnote_ids` 单独关联说明。已知单位从末尾括号提取；“包含热泵系统”等描述不会被当成单位。保留 `55/70`、`●`、`○`、`-`，不推断含义或拆分选装组合。

从仓库根目录运行。输出必须是新文件，不能写到原始资料目录：

```powershell
& .\.tools\uv\bin\uv.exe run --locked --offline --cache-dir .uv-cache python -m car_knowledge_rag.parse_config 20261104T061714920392Z-70f8b89f/10/config --manifest data/manifests/zeekr/20261105T043319757600Z/manifest.json --output data/parsed/zeekr/9x-b4-new.json
```

解析器先核对清单中 HTML 和页面回执的大小与 SHA-256，再检查采集状态、来源身份、表头顺序、分组跨度、每行单元格数及脚注。失败时不会写出新的解析结果。哈希只能验证文件与基准一致，不能验证官网参数本身。

本次产物为 `data/parsed/zeekr/9x-b4-verified.json`，已加入 Git 忽略范围。得到 7 列、277 行、1,939 个单元格和 14 条编号脚注。对照原表抽查：座位行前四列为 6 人、后三列为 5 人；六座 Ultra 版电池保留 `55/70`；CLTC 纯电续航关联脚注 1；主动稳定杆保留选装符号 `○`。这不是对所有单元格的人工核验。
